# 标题：解决 WSL 仿真环境下开启 use_sim_time 导致 ROS 2 节点定时器假死的问题
# 涉及层次：环境、配置、代码

## 1. 背景
- 目标：为了让中枢节点与 Gazebo 仿真环境保持严格的时间同步，防止因电脑真实时间与虚拟仿真时间不一致导致的数据乱序，尝试在 ROS 2 的 launch 文件中为中枢节点开启 `use_sim_time:=true` 参数。
- 遇到的具体问题：开启该参数后，中枢节点能正常接收终端发送的假数据并打印日志，但 `timer_callback` 定时器彻底静默，不发任何数据。而将 `use_sim_time` 关闭（使用系统默认真实时间）时，一切恢复正常，飞机正常起飞。
- 为什么这个问题值得记录：这是一个极其隐蔽的底层环境 Bug。网络通信、代码逻辑、坐标系转换、话题名称全部正常，仅仅因为时钟源的挂载问题导致定时器死锁，极易让开发者在业务代码中疯狂排查而忽略底层时间机制。

## 2. 排查过程
- 现象：中枢节点终端疯狂打印“收到规划目标”，但发送给飞控的桥接节点终端没有任何接收日志，飞机悬停不动。使用 `ros2 topic echo` 监控中枢输出话题，一片空白。
- 尝试过的方法（包括失败的）：
  1. 检查话题名称是否匹配（确认中枢发和桥接收均为 `/drone_1/fmu/in/trajectory_setpoint`）。
  2. 检查 ROS_DOMAIN_ID 是否一致（均为 0）。
  3. 在回调函数、辅助函数、定时器中加入大量的 `🔥🔥🔥` 打印语句进行追踪。
  4. 尝试严格按照“先开 Gazebo，再开中枢”的顺序启动，依然失败。
- 关键线索：
  - 加入探针后发现，中枢的 `timer_callback` 连最开头的一句打印都没有输出，说明 20Hz 的定时器根本没有被执行。
  - 使用 `ros2 run` 绕过 Launch 文件直接启动中枢节点，不传入 `use_sim_time`，所有探针全部打印，数据瞬间发出，无人机起飞。
- 根本原因：在当前的 WSL 环境下，当 ROS 2 节点被强制开启 `use_sim_time` 时，它会等待并挂载 Gazebo 发布的 `/clock` 话题。但由于 WSL 底层的网络与时钟机制存在兼容性问题，节点未能成功捕获时钟信号，导致 ROS 2 内部的定时器（`create_timer`）挂起死锁，彻底停止跳动。

## 3. 解决方案
- 具体步骤：在当前纯软件测试与 WSL 仿真阶段，暂时放弃使用仿真时间基准，强制全系统统一使用电脑的真实系统时间。
- 关键命令/代码片段：
  在 launch 文件中，将 `use_sim_time` 的参数注释掉：
  ```python
  from launch import LaunchDescription
  from launch_ros.actions import Node
  
  def generate_launch_description():
      return LaunchDescription([
          Node(
              package='center_node_pkg',
              executable='center_node',
              name='center_node',
              output='screen',
              # 注释掉该参数，避免 WSL 下定时器假死
              # parameters=[
              #     {'use_sim_time': True} 
              # ]
          )
      ])
  ```
- 需要注意的坑：在禁用仿真时间后，所有节点（包括假数据节点）发出的 `header.stamp` 都会自动带上系统的真实时间。此时中枢节点的“延迟过滤安检门”依然能正常计算差值，不受影响。
- **转折：意识到代码逻辑和通信完全没有问题，问题出在操作系统的时钟挂载底层机制上，果断放弃死磕仿真时间。

## 4. 验证
- 验证方式：移除 launch 文件中的 `use_sim_time` 参数后，重新编译并启动中枢节点，同时运行假规划节点和假桥接节点。
- 结果：中枢终端瞬间打印出“🔥🔥🔥 数据已发出”，底层桥接节点成功收到坐标，Gazebo 中的无人机精准飞向目标点。系统完全恢复正常。

## 5. 总结与反思
- 这次学到的：时间无法通过检查可能只是因为底层时钟出了深层的bug
- 下次遇到类似问题，先检查什么：先排查是否是自身架构或代码逻辑问题，再考虑底层bug（虽然最近好多问题都是因为底层bug（悲））

## 6. 核心概念

1. **use_sim_time**
   这是 ROS 2 节点的一个系统级参数。默认情况下，节点使用电脑主板的真实物理时间（Wall Time）。当它被设置为 `true` 时，节点会停止使用真实时间，转而监听并同步仿真器（如 Gazebo）发布的 `/clock` 话题。如果 `/clock` 数据未成功接收，节点的所有与时间相关的操作都会停滞。

2. **定时器假死**
   在 ROS 2 中，定时器（Timer）依赖于底层的时间源来触发。当外部时间源中断（或者如本例中因环境兼容问题无法挂载），`create_timer` 注册的回调函数将永远不会被放入事件循环，表现为“节点活着、能收消息，但相关的定时循环彻底静默”。
